# Go2 网络抖动诊断报告（2026-10-21）

诊断者: go2 网络诊断 agent。**只读诊断，未改任何代码/服务**。
板钟无 RTC（上一次 boot 开头有 2023-11-21 假时间戳），本文时间以板钟 UTC 为准，**相对顺序可靠、绝对时刻存疑**。

## 0. 结论速览

1. **板↔交换机段被高置信排除**：全部采样窗口内 carrier=1、carrier_changes 冻结在 boot 值 4、eth0 收发 0 错误 0 丢包、dmesg 无任何 link 事件、neigh 从未 FAILED。用户看到的"灯闪 5 秒掉几秒"**不是板口链路在掉**。
2. 抖动位于**交换机↔狗 / 狗内部网络 / 狗应用层**三选一（或组合）。其中**狗应用层(9991/webrtc_bridge)有正面实测证据**（单探失败 3 秒即恢复、心跳无回包、WebRTC InvalidStateError），物理段（交换机↔狗）只有用户目击"狗口灯闪"支持，且**未区分 link 灯 vs 活动灯**——活动灯在狗不回包时熄灭是正常现象，是最强的混淆项。
3. 故障实为**两族独立问题**：
   - **族① 闪断风暴**（20-30 分钟级别、间歇、狗侧）：风暴期只有 9991/心跳/WebRTC 掉，ping 基本 0% 丢，3 秒级自愈；
   - **族② 板子 unclean 重启**（10-14 boot 环、10-20 07:06 异常断电、今天 01:25 unclean）：上装板由**狗 M8 扩展线 12V 对外口**供电（`ARCHITECTURE.md:133`），该口已被 A0 事故证明会在电流冲击时保护性断电（`TODO.md:6-31`）。
4. 用户怀疑的"高温"：板 SoC 49°C 正常；狗 IMU 79°C 是**每次首连即如此**（含安静期），不是风暴独有，暂无正向证据，但也没有排除手段——需与电池电压一起做风暴时刻对照（D-V2）。

## B. 抖动到底发生在哪一段

拓扑（由 E6 多子网同 L2 + CLAUDE.md:37 板 eth0=123.50+144.10 别名推断）：

```
板 eth0 (100M/Full, d8:4c:df:fe:ac:a1)
   │ 网线A
交换机（用户目击"狗口"灯闪 5s/灭几秒，反复；室内同样）
   │ 网线B
狗 eth 口 (192.168.123.161, MAC 7e:1d:75:60:f5:89 为本地管理地址=狗内桥)
   └─ 狗内桥：123.x / 144.x(.11 计算模块 00:66:53:11:97:56) / 169.254.x
上装板供电 ⇐ 狗 M8 扩展线 12V 对外口（E11，独立故障源）
```

逐段判定：

| 段 | 判定 | 依据 |
|---|---|---|
| 板↔交换机 | **排除（高置信）** | 全窗口 carrier=1、cc=4 冻结、transns=4、0 err/0 drop、dmesg 无事件（E1-E4）；风暴期看门狗 1s 载波检查也从未打出"载波丢失"（E8 全文无此行） |
| 交换机↔狗（物理） | **候选，未定案** | 仅用户/TODO 目击狗口灯闪（E12、题设）。反证缺失：风暴期无 ping/neigh 采样；若真是此段掉几秒，应见 ping 突发丢失 + neigh FAILED + ARP 重解析——**这正是 D-V1 要补的数据**。强混淆项：未确认是 link 灯还是活动灯；活动灯随流量闪烁，狗应用层卡顿时灯"灭几秒"完全正常 |
| 狗内部网络 | **候选，无直接计数器** | 无狗侧 SSH；狗内桥同时挂 123/144/169.254 三网（E6），任一内部组件劣化都会表现为对外 9991 间歇不通而 ping（同桥转发）受影响较小 |
| 狗应用层(9991/webrtc_bridge) | **有正面实测证据，当前最可能** | 风暴期 9991 单探失败 3s 自愈 ×5、心跳无回包 ×3、InvalidStateError、LocalSignalingPortError（E8/E9）；ping 通常 0%（题设+E1）；`bridge.py:361-363` 注释实测"狗在起立/忙时 9991 可能瞬时限连"；10-20 换 2-miss 容忍后风暴不再拆会话=风暴烈度本就在"单次探测超时"量级 |

**结论：故障不在板侧。三段候选中，所有能落表的实测失败都落在狗应用层与狗侧；物理段（交换机↔狗/狗内）只有目击证据且与活动灯混淆未剥离。** 族②（板 unclean 重启）与族①闪断是两码事：风暴期间板从未重启（同 PID/同 boot 贯穿 11:22→11:32），族②由狗 12V 口供电特性解释（E11）。

## D. 可执行验证步骤（按成本升序，≤6）

> 每步都只读/可逆，不改桥行为。判据均以"下一场风暴"为观测对象——风暴是间歇的（10-20 一场 10 分钟，间隔可达 14h+），验证要有耐心或主动复现（连续操控 20-30 分钟）。

**V1（0 成本，风暴时 3 分钟定案：物理 or 应用层）**
风暴出现时（灯闪/遥控不灵），在板上读 `/tmp/netmon_long.log`（若已到期则重跑同样脚本，源码见 E2）：
```bash
tail -f /tmp/netmon_long.log        # 看 tcp/ping/neigh 三列
grep -c "ping=0" /tmp/netmon_long.log
```
- 判据 A：`ping=0` 连续成串 + `neigh` 出现 `FAILED/INCOMPLETE` ⇒ 物理段断（交换机↔狗或狗内），H1 出局，进 V3/V4 分段；
- 判据 B：`tcp=0` 而 `ping=1` 且 neigh 恒 `REACHABLE` ⇒ **狗应用层（H1）实锤**；
- 同时用手机拍下灯：**确认是 link 灯（常亮型）还是活动灯（闪烁型）**、是狗口还是板口——link 灯灭=物理断，活动灯灭只是没流量。

**V2（0 成本，判 H3/H2：狗侧状态对照）**
风暴时刻与安静期各截一次桥调试台（:8000 的 /state 与"狗真实姿态"面板，10-20 已落地）里的 IMU 温度/狗自报状态，另从 sportmodestate 流可读电池电压（狗侧数据已在订阅中，纯读）：
- 判据：风暴时电池电压较安静期掉 >0.3~0.5V 或温度单边爬升 ⇒ H3/H2 加权；纹丝不动 ⇒ 降温/供电假设降权。

**V3（5 分钟，判 H4 网线）**
换一根已知好的短网线接狗↔交换机，两端重插，最好换一个交换机端口：
- 判据：连续 2-3 个使用会话风暴消失 ⇒ 网线/接头；无变化 ⇒ 回到狗侧。

**V4（10 分钟，判 H5 交换机）**
板↔狗用一根网线**直连**（绕开交换机；地址同网段 123.x 无需改配置）：
- 判据：直连下风暴消失 ⇒ 交换机（H5）；仍风暴 ⇒ 狗侧（H1/H2/H3），物理段排除。

**V5（10 分钟，判 H1 应用层，双端对照）**
第三台设备（PC 接同一交换机）在风暴时同时打：
```bash
ping -i 0.2 192.168.123.161          # 高频 ping
while true; do timeout 2 bash -c 'echo > /dev/tcp/192.168.123.161/9991' && echo OK || echo FAIL; sleep 1; done
```
- 判据：PC 与板同刻 FAIL 且 ping 同刻丢 ⇒ 狗侧全局（物理或内部）；仅 9991 FAIL 而 ping 双端都通 ⇒ H1 实锤且与板无关。

**V6（30 分钟，族②收尾，判 H7）**
上装板改独立 5V 供电（充电宝/独立 USB 电源，A0 硬件方案 1；`TODO.md:27-30`），狗 12V 口只留飞控/接收机：

## I. 2026-10-21 10:14 定案：根因是狗网卡 EEE，关闭后链路 5 分半零抖动

> 狗 09:59 断电重启（autoneg 恢复 on）后**抖动照旧**：
> 开机 5 分钟 `carrier_changes=40`，dmesg 每 5~15 秒一组
> `Link is Down` → 恰好 ~3.0 秒后 `Link is Up - 100Mbps/Full`。
> 3.0 秒是自协商重建时间，所以"掉几秒"不是接触不良的随机时长，而是每次都在重新协商。
> PC→狗 ping 60s 丢 2/4。

排除项（本轮新增证据）：
- 板侧 eth0 接同一交换机：`carrier_changes=4` 全程冻结、0 error/drop → **交换机没有重启/掉电**，"换过口"的判断成立。
- 狗 PCI 电源管理：`power/control=on`、`runtime_status=active`，无 ASPM → 不是 PCIe 省电。
- Unitree `net_switcher.py`（正在运行）只操作 wlan0/wwan0，全文无 eth0 → 不是 4G/网络模式切换脚本。
- 狗温度 44.4~45.3°C、负载正常 → 不是高温。
- `ip -s link` RX errors/dropped 全 0 → 不是线缆信号质量（坏线通常先出 CRC 错）。
- 交换机只广告 10/100（协商到 100M/Full），速率本身正常。

**决定性变量**：`ethtool --show-eee eth0` = **EEE status: enabled - active**，
双方都广告 `100baseT/Full` EEE；板载网卡不做 EEE → 解释了"只有狗这口抖、板子这口稳"。

实验（10:14:50，仅运行时设置）：
```
ethtool --set-eee eth0 eee off
```
- 触发一次 link 重建（10:14:50 Down → 10:14:52 Up），此后 **carrier_changes 冻结在 74，
  到 10:31:34（16 分 42 秒，跨 5 分钟采样 + 10 分钟长测）零 Down/Up**；关闭前最长安静间隔只有 72 秒。
- PC→狗 ping 240 包 **0 丢失、0ms**，随后 10 分钟长测 **600 包 0 丢失**（关闭前同链路 60 包丢 2）。
- 桥 `link_gen` 同步停在 11，17 分钟无重连（关闭前 17 分钟 10 次）。

结论：RTL8168 的 EEE 与这只 10/100 交换机组合导致周期性链路重协商，是本次"交换机灯闪 5 秒掉几秒"
和"延迟巨大/吞指令"的根因；桥的心跳超时、强制上锁只是次生放大。

**持久化（2026-10-21 11:21，用户批准后安装）**：狗用 ifupdown（`/etc/network/interfaces.d/eth0`），
已写入 `/etc/network/if-up.d/eee-off`（755，eth0 ifup 时执行
`/usr/sbin/ethtool --set-eee eth0 eee off`，并用 logger -t eee-off 留痕）。
可逆：删除该文件并重启即可；当前会话也可 `ethtool --set-eee eth0 eee on` 立即恢复。
下次狗重启后 `journalctl -t eee-off` 应出现 "eth0 EEE disabled"，且 `carrier_changes` 不再增长。
若 EEE 关闭后仍出现 flap，再走 V4 直连 / 换线换口。
